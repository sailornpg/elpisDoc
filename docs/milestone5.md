## 1. 总体说明

结合当前项目代码结构来看，这个项目已经不再是单一业务工程，而是被整理成了一个可复用、可发布的框架型包。其核心目标，是把原本耦合在业务项目中的启动逻辑、目录约定、前端构建能力、动态页面渲染能力抽离出来，沉淀为一个可以通过 `npm install` 直接引入的公共包。

从仓库现状看，项目已经完成了较明确的“包分离”动作，并具备了发布为 npm 包的基础条件。当前包名为 `@sailornpg/elpis`。

## 2. 包分离都做了什么

### 2.1 将框架内核从业务实现中抽离

当前项目最关键的包分离动作，是把框架核心能力从具体业务代码中抽离出来，形成了相对独立的框架内核。

具体表现为：

- 将服务端启动核心集中在 `elpis-core/` 目录下。
- 将中间件、路由、控制器、服务、配置、扩展等加载机制抽象为统一 loader。
- 将外部业务项目约定为在运行时通过 `process.cwd()` 注入，而不是写死在框架代码里。

这意味着框架本身负责“怎么启动、怎么装配、怎么加载”，业务项目只负责“提供自己的 app 目录和业务配置”。

这一点本质上完成了从“项目代码”到“框架代码”的第一次分层。

## 2.2 统一对外暴露入口

根目录 [index.js](/D:/学习/elpis/index.js) 已经承担 npm 包主入口职责，对外统一暴露了几类能力：

- `serverStart`
- `frontendBuild`
- `Controller.Base`
- `Service.Base`

这一步很重要，因为它把原来内部多个目录的实现收敛成稳定 API，外部使用者不需要了解内部目录细节，只需要通过包入口按约定调用即可。

这说明拆包时已经完成了“内部实现”和“对外接口”的边界整理。

## 2.3 把服务端启动能力产品化

在当前代码里，服务端启动不再要求业务方自己组装 Koa、路由和加载顺序，而是统一通过：

```js
const { serverStart } = require("@sailornpg/elpis");

serverStart();
```

来完成启动。

这背后已经抽离出一整套通用服务端能力，包括：

- 环境初始化
- 中间件加载
- router-schema 加载
- controller 加载
- service 加载
- config 加载
- extend 加载
- 业务全局 middleware 加载
- 框架全局 middleware 加载
- 路由注册

也就是说，包分离过程中已经把原本散落在业务工程中的启动编排逻辑收敛成了统一框架能力。

## 2.4 把前端构建能力产品化

当前项目不仅拆出了后端框架，也拆出了前端构建入口。外部项目可以直接通过：

```js
const { frontendBuild } = require("@sailornpg/elpis");

frontendBuild(process.env._ENV);
```

调用框架内置的 Webpack 构建能力。

这说明拆包时已经把以下能力沉淀到包内部：

- 开发环境构建入口
- 生产环境构建入口
- 通用 Webpack 基础配置
- 页面入口扫描机制
- 模板输出机制
- 业务扩展 alias 注入机制

这一层很关键，因为它标志着这个包不是单纯的后端 npm 包，而是一个同时承载服务端启动和前端页面构建的全栈框架包。

## 2.5 抽离业务扩展点，而不是把业务写进框架

Webpack 配置中已经明显体现出拆包思路不是“把所有东西封死”，而是预留扩展点让业务方接入。

当前已经支持的扩展点包括：

- dashboard 路由扩展
- schema-view 业务组件扩展
- schema-form 表单组件扩展
- schema-search-bar 搜索组件扩展

并且通过空模块兜底的方式，让这些扩展成为“可选能力”，即：

- 有业务实现时加载业务实现
- 没有业务实现时加载空模块，保证框架仍能正常运行

这一点说明拆包过程中已经处理了平台层与业务层解耦问题，而不是简单做目录搬运。

## 2.6 通过约定式目录实现框架复用

当前包分离后，业务项目需要遵循统一目录约定，例如：

- `app/controller`
- `app/service`
- `app/router`
- `app/router-schema`
- `app/config`
- `app/extend`
- `app/pages`

框架通过 loader 和构建配置自动扫描这些目录。

这种设计说明拆包做的不是“函数级工具抽取”，而是“工程级约定抽象”。它把业务项目的接入方式标准化了，从而让框架真正具备跨项目复用能力。
